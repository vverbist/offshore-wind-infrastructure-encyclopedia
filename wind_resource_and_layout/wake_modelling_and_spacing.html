Wake Modelling and Spacing

Role in the Model

This calculation turns turbine coordinates, a tabulated turbine curve and a set of wind states into the wake-affected electrical power of every turbine in every state. That table is the common input to all architectures: it gives power at the generator electrical output, before any architecture-specific conversion or collection loss. The implementation is calculate_wakes in model/wind_resource_and_layout/wake_modelling_and_spacing.py.

The layout is deliberately schematic. It exposes the relationship between installed capacity, occupied area, turbine separation and wake loss without claiming to reproduce a consented or commercially optimised wind-farm layout.

Inputs

Symbol Description Unit Source in the model
\((x_j,y_j)\) Turbine coordinates, \(x\) east and \(y\) north m Scenario coordinates file, or a declared regular grid
\(P(v)\), \(C_T(v)\) Tabulated electrical power and thrust coefficient kW, – Scenario turbine-curve file
\(D\), \(H_h\) Rotor diameter and hub height m Scenario turbine record
\(v_s\), \(\theta_s\), \(h_s\) Wind speed, direction (wind from, clockwise from north) and annual hours of state \(s\) m/s, °, h/year Scenario wind-state file
\(I_0\) Ambient turbulence intensity fraction 5.8% (provisional legacy assumption)

The state hours must add up to the central annual-hour basis (8760 h/year); they are not renormalised.

Layout

A scenario supplies coordinates directly, or declares a regular grid (turbine count, columns, spacings and rotation) whose incomplete final row is centred. In both cases the model checks that every pair of turbines is at least the declared minimum separation apart and rejects the layout otherwise. Farm area is a reporting boundary; it is never used as a multiplier on distances.

The article reference case generates its coordinates from the agreed site record: a rectangle across the dominant wind direction, rows numbered from the upwind edge and an explicit rotation convention (see the reference case).

Turbine Performance

The wake calculation uses a supplied, tabulated power and thrust-coefficient curve; it never builds a synthetic curve. The article case uses the pinned IEA 15 MW reference turbine release (Gaertner et al. 2020; IEA Wind TCP Task 37 2026), whose power column is electrical output. Zero power and thrust are declared just outside the operating range, because PyWake would otherwise hold the first tabulated value for waked turbines below cut-in.

Wake Calculation

PyWake evaluates every state with the following configuration (DTU Wind and Energy Systems 2026):

Model element Selection Function
Site UniformSite with ambient \(I_0\) Uniform inflow; state weights come from the wind-state table, not from the site
Propagation PropagateDownwind Calculates wakes from upstream to downstream turbines
Wake deficit TurboNOJDeficit Turbulence-dependent top-hat wake expansion (Nygaard et al. 2020)
Rotor averaging AreaOverlapAvgModel, on the deficit model Partial overlap of a top-hat wake and a downstream rotor
Superposition SquaredSum Combines deficits from several upstream turbines
Blockage None Upstream induction is excluded

The calculation is run once per wind direction for all speeds in that direction; each state keeps its own speed and weight. For state \(s\) and turbine \(j\) the result is the wake-affected power \(P_{j,s}\) in kW. The installed PyWake version is recorded with each result.

Annual Energy and Outputs

The wake-affected and no-wake annual energies, in MWh/year, are

\[ E_\mathrm{wake}=\frac{1}{1000}\sum_s h_s\sum_j P_{j,s}, \qquad E_0=\frac{N}{1000}\sum_s h_s\,P(v_s), \]

and the wake loss and wake-affected gross capacity factor are

\[ L_\mathrm{wake}=1-\frac{E_\mathrm{wake}}{E_0}, \qquad CF_\mathrm{wake,gross}=\frac{1000\,E_\mathrm{wake}}{NP_r\,\sum_s h_s}. \]

These exclude availability, collection, conversion and export losses, which are applied downstream and must not be applied again here. For the article reference case the result is a wake loss of 10.0% and a gross capacity factor of 54.7%.

The model accepts the wind input in two equivalent forms: a wind-state table with a turbine curve, from which it runs PyWake itself (optional wind dependency), or a stored table of per-turbine power by state. The article case stores the table, generated with the same function by research_articles/turbine_level_hydrogen/analysis/prepare_common_case.py, so that both architectures read identical turbine power and a case run does not need PyWake. A zero-hour design state may be added for peak-duty sizing.

Legacy Implementation

The earlier model used a synthetic ramp-shaped power curve with a constant thrust coefficient, PyWake’s UniformWeibullSite with sector-edge directions, a fixed 30° orientation and a grid truncated after \(N\) positions. These are replaced by the method above and are retained only for traceability of older results.

WarningRemaining improvements
  1. Benchmark the wake model. Compare representative dense and sparse layouts against at least one credible alternative wake formulation and use the difference as model uncertainty.
  2. Test turbulence and blockage sensitivity. The provisional \(I_0\) directly affects TurboNOJDeficit; evaluate a sourced range and quantify whether the omission of blockage changes the comparison.
  3. Source the minimum-separation check. The article case keeps the unsourced legacy threshold of three rotor diameters as a coordinate check only.

Higher-fidelity CFD, LES and full commercial layout optimisation are not proposed at this stage. They are justified only if the simpler model has first been made internally consistent and the remaining wake uncertainty can materially change the comparison.
